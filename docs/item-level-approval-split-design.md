# 設計書：明細単位の承認と部分差戻し（申請の分割）

対象要望（スタッフ）:

- 申請書には明細を複数入れられる。「項目全体の承認」に加えて「項目ごとの承認」「項目1つずつの差し戻し」をしたい。
- 4項目のうち1項目が差戻しになったら、**その1項目だけを別の申請1枚にまとめ直して差戻しプールへ移し、残り3項目はそのまま承認プロセスを進める**。申請書が1枚から2枚に分離するイメージ。

決定事項（2026-07-25 合意）:

| 論点 | 決定 |
|---|---|
| 分割を許可するステップ | **上席／購買見積／総務部長／社長**（購買手配は不可） |
| 分割で合計額が下がったときの元申請 | **常にそのまま進む**（金額だけ再計算し、経路は変えない） |
| 「項目ごとの承認」のUI | **承認パネルのチェックボックスに統合**（既定は全チェック＝従来の全体承認） |

---

## 0. 方式選定：なぜ「分割」なのか

対案として「明細に承認状態の列を持たせる（分割しない）」も検討したが、採用しない。

現行はワークフローの状態（`status` / `currentStep` / `currentApproverEmail` / `routeJson`）がすべて**申請シートの1行**にあり、申請明細シートは状態を一切持たない子レコードである。PDF・ハンコ・経路・金額・メール・履歴も全部が申請単位に組まれている。明細に状態を持たせると、そのすべてを明細単位に作り替えることになる。

一方**分割方式は既存の仕組みを一切変えない**。差戻しプールは `status === 差戻し` の申請を並べるだけ（`getRequests` の `mode: 'returned'`）なので、分離した明細を「1明細だけの差戻し済み申請」として作れば、プールの表示・編集・再提出・削除・件数バッジがそのまま動く。**新しいタブも新しい状態も不要。** ご提案の方向性を採用する。

## 1. 全体の流れ

```
【分割前】REQ-A（総務部長ステップ・4明細・11万円）
              │
              │ 総務部長が明細3のチェックを外して「3件を承認し、1件を差戻し」
              ▼
【分割後】REQ-A（社長ステップへ進む・3明細・8万円）   REQ-B（差戻しプール・1明細・金額0）
          ・承認履歴はそのまま引き継ぐ                 ・splitFromRequestId = REQ-A
          ・「明細分離」履歴が1件増える                 ・履歴は「差戻」1件（理由付き）
          ・PDFを再生成                                ・誰でも編集・再提出・削除できる
```

分離された REQ-B は**通常の差戻し済み申請と完全に同じもの**として扱う。再提出すれば `resubmitRequest` が経路を上席から組み直す（既存実装のまま）。

## 2. スキーマ変更

### 2-1. 申請シート（末尾に1列追加）

```js
var REQUEST_COLUMNS = [ ...既存..., 'splitFromRequestId' ];
var REQUEST_HEADERS  = [ ...既存..., '分離元申請ID' ];
```

**末尾に追加すること**（読み書きが列位置ベースのため）。`ensureSheet_` が列を自動追加するので手動移行は不要。既存行は空欄。
逆引き（元 → 分離先）は履歴コメントと本列の検索で辿れるため、元申請側に列は追加しない。

### 2-2. 操作コード

```js
var ACTION = Object.freeze({ ...既存..., SPLIT_OUT: '明細分離' });
var ACTION_LABELS = Object.freeze({ ...既存..., '明細分離': '明細を分離' });
```

クライアント側の `HIST_GLYPH` に `'明細分離': '⑃'`、`ACTION_CLASS` に `'明細分離': 'RETURN'` を追加する。

### 2-3. 分離先申請（REQ-B）の初期値

| 列 | 値 |
|---|---|
| `requestId` | 新規発番 |
| `applicantEmail` / `applicantName` / `department` / `category` / `reasonCode` / `reasonDetail` / `requestDate` / `submittedAt` | **元申請から複製**（申請者本人の申請として、元の申請日のまま残す） |
| `status` / `currentStep` | `差戻し` / `申請者` |
| `totalAmount` | `0`（単価もリセット。差戻し＝やり直しのため。`resubmitRequest` が合計を0にする既存挙動と揃える） |
| `routeJson` | 標準経路。再提出時に `resubmitRequest` が組み直す |
| `amountWaived` | `false` |
| `pdfFileId` / `pdfUrl` | 空（差戻し中はPDFを持たない） |
| `splitFromRequestId` | 元申請ID |
| 明細 | 選択された明細のみ。`lineNo` を1から振り直し、`unitPrice`／`amount` は0、**単位はそのまま引き継ぐ** |

## 3. 実装上の必須要件

### 3-1. `itemId` は永続IDではない（最重要）

`replaceItems_`（`Storage.gs:272`）は明細を**全削除して再挿入し、`itemId` を毎回新規発番する**。現状 `itemId` を使うのは `confirmQuote` と見積パネルだけで、1往復内に閉じているため問題化していない。

明細を指す新APIでは、画面表示から操作までの間に他者が明細を編集すると**別の明細を差し戻す**危険がある。したがって:

- クライアントは `{ itemId, lineNo, name }` の**3点セット**を送る。
- サーバはロック内で最新の明細を読み直し、3点すべてが一致する行だけを対象にする。
- 1件でも一致しなければ**処理全体を中断**し、「他の人が明細を更新した可能性があります。画面を再読込してやり直してください」を返す（部分的に実行しない）。

### 3-2. 明細0件は不正

`normalizeRequestPayload_` / `normalizeEditableItems_` は明細1行以上を強制している。したがって:

- **全明細の選択解除は禁止**。「すべての明細を差し戻す場合は、申請全体の差戻しをご利用ください」でエラーにする。
- クライアント側でも全解除時はボタンを無効化し、理由を表示する。

### 3-3. 分離時はPDFを再生成する

`dispatchApprovalNotifications_` がPDFを生成するのは、次ステップが `購買見積` / `購買手配` / `完了` のときだけである。**総務部長 → 社長 の遷移ではPDFを生成しない。**
分割で明細が変わった以上、元申請のPDFは必ず作り直す必要があるため、**分割が起きて元申請に `pdfFileId` があれば `createRequestPdfInternal_` を明示的に呼ぶ**（上席ステップではまだPDFが無いので不要）。

### 3-4. 差戻し理由は分離先の履歴に「差戻」として残す

詳細画面のプールパネルは差戻し理由を `history.filter(h => h.action === '差戻').slice(-1)[0]` で拾っている（`Client.html:643`）。
分離先（REQ-B）の履歴に **`action: 差戻` の行を1件作る**ことで、既存UIがそのまま理由を表示できる。

- REQ-B の履歴: `action: 差戻` / `fromStep: 分割時点の元申請のステップ` / `toStep: 申請者` / `comment: 理由 ＋「REQ-A の明細3から分離」`
- REQ-A の履歴: `action: 明細分離` / ステップは変えず / `comment: 「明細3「品名」を REQ-B として差し戻し（理由）」`

### 3-5. 分離時の理由コメントは必須

通常の差戻しと同じ扱い（`returnRequest` は空コメントを弾いている）。分離もコメント必須とする。

## 4. サーバ実装

### 4-1. 共通コア（書き込みを伴わない検証と、分離先の生成を分ける）

```js
// 選択された明細参照を検証し、移動対象と残留対象に振り分ける（書き込みはしない）。
// refs: [{ itemId, lineNo, name }]
// 戻り値: { moved: [...], remaining: [...] }
function resolveSplitSelection_(request, refs)

// 分離先の申請・明細・履歴を作る。戻り値: 新しい requestId。
function createReturnedSplitRequest_(request, movedItems, comment, user)
```

### 4-2. 各承認関数への組み込み

分割は**承認と同じ操作の中で**行う（別操作にしない）。各エントリポイントは共通の順序に従う:

1. ロック取得 → 権限チェック → **分割可能ステップかの確認**
2. `resolveSplitSelection_` で検証（不一致なら中断。ここまで書き込みは一切しない）
3. `createReturnedSplitRequest_` で**分離先を先に作成**（申請行・明細・履歴のみ。通知はまだ送らない）
4. **残明細を書き戻す**（`replaceItems_`。見積時はここで単価を適用する）
5. `totalAmount` を残明細の金額合計で再計算
6. 元申請へ「明細分離」履歴
7. **通常の承認処理を継続**（ステップ遷移・履歴・通知）
8. 分離が起きて `pdfFileId` があればPDF再生成
9. `notifySplitReturned_` で分離先の通知（`sendReturnedEmail_` と `sendReturnedBroadcast_`）

> **3 と 4 の順序が重要**：GAS にトランザクションは無く、スプレッドシート書き込みは一時エラーで落ちうる。
> 元申請から明細を削ってから分離先の作成に失敗すると、**その明細はどこにも存在しなくなり復元できない**。
> 逆順なら最悪「両方に同じ明細がある」だけで済み、人手で戻せる。**消失より重複を選ぶ。**
> 同じ理由で通知（9）は全書き込みの完了後に送る。途中で失敗した中途半端な状態でメールだけ飛ぶのを避ける。

> **順序が重要**：`replaceItems_` は残明細の `itemId` も付け直すため、単価の適用（見積）は必ず**書き戻しと同じ1回の呼び出し**で行う。先に分割して後から単価を書くと、古い `itemId` を参照して単価が付かない。

| ステップ | 呼び出し口 | 金額の扱い |
|---|---|---|
| 上席 | `approveRequest` に `returnItems` を追加 | 未確定。`totalAmount` は0のまま |
| 購買見積 | `confirmQuote` に `returnItems` を追加 | **残明細の単価だけを適用**して合計を出す。しきい値判定も残明細の合計で行われるため自然に正しくなる |
| 総務部長 | `approveRequest` に `returnItems` を追加 | 確定済み。残明細の `amount` 合計で再計算 |
| 社長 | `approveRequest` に `returnItems` を追加 | 同上 |
| 購買手配 | **対応しない** | — |

> 実装時の確認事項：詳細画面の承認パネルは**ステップを問わず `approveRequest` を呼んでいる**（`recordPresidentDecision` は全画面モード専用の入口）。社長ステップの分割も `approveRequest` を通る。
> `recordPresidentDecision` にも `returnItems` を受ける口を用意してあるが、全画面モードを分割非対応にしたため現状クライアントからは使われない（将来、全画面モードを対応させる場合の受け口として残す）。

### 4-3. 経路は変えない（決定事項）

**金額確定後（総務部長・社長ステップ）の分割**では、合計が社長決裁しきい値（税抜10万円）を下回っても
**`routeJson` は変更しない**。11万円→8万円になっても社長決裁を経由する。

> **例外：購買見積ステップ。** ここは金額を初めて確定させる工程で、`confirmQuote` が確定額から
> 経路を新しく組み直す（既存挙動）。分割した場合の確定額は残明細の合計なので、**高額な明細を分離して
> しきい値未満になれば社長決裁は付かない**。これは「まだ確定していない金額の経路を決める」動作であり、
> 「確定済みの承認を後から覆す」上記の論点とは別物のため、既存挙動のままでよい。

これは安全側の選択である。分割で金額が増えることはないため、この方針で「本来必要な承認が飛ばされる」ことは起こり得ない。起こり得るのは「本来不要な社長決裁を通す」だけであり、承認過多は監査上の欠陥にならない。実装も単純になる。

### 4-4. キオスク（全画面承認モード）では分割しない

全画面モード（社長決裁モード）は申請書をA4比率で提示する画面で、明細ごとのチェックボックスを置く余地がない。またタブレットを相手に渡した状態での複雑な選択操作は誤操作のリスクが高い。
**全画面モードは従来どおり「全体承認／全体差戻し」のみ**とし、分割は詳細画面の承認パネルからのみ行う。

## 5. UI設計

### 5-1. 承認パネル（上席・総務部長・社長）

現在の承認パネルは明細テーブルを持たない（明細は下の「申請明細」カードにある）。**承認パネル内に選択用の明細リストを追加する**——操作とその対象を隣接させ、「何を承認し何を戻すのか」を一目で分かるようにする。

```
┌─ あなたの承認待ち ─────────────── 総務部長として承認 ─┐
│ ⚠ 承認は責任を伴います（既存の注意書き）                    │
│                                                            │
│ 承認する明細を選んでください（既定は全件承認）              │
│  ☑ 1. 六角ボルト M8×20        100 個                       │
│  ☑ 2. ウエス（白）             10 kg                       │
│  ☐ 3. 電動ドリル              1 台   ← 差戻し             │
│  ☑ 4. 作動油 ISO VG32          4 缶                        │
│                                                            │
│ ⚠ 差し戻し時の注記（既存）                                 │
│ [ 承認・差戻しコメント ______________________ ]            │
│   差し戻す明細がある場合、理由は必須です                    │
│                                                            │
│  🗑 申請を取消        ✕却下  ‹全体を差戻し  ✓ 3件を承認し1件を差戻し │
└────────────────────────────────────────────────────────────┘
```

- 既定は**全チェック**。この状態のボタンは従来どおり「✓ 承認する」。
- 1件でも外すと、ボタンが「**✓ 3件を承認し、1件を差戻し**」に変わり、コメント欄が必須になる。
- 全件外すとボタンを無効化し、「すべて差し戻す場合は『全体を差戻し』を使ってください」と表示する。
- 実行前に `window.confirm` で「明細3「電動ドリル」を新しい申請として差戻しプールへ移し、残り3件を承認します。よろしいですか？」と確認する。

### 5-2. 見積パネル（購買見積）

既に明細テーブルがあるので、**行頭にチェックボックス列を足すだけ**。外した行は単価入力を無効化・グレーアウトし、小計・消費税・合計の自動計算から除外する（`bindQuotePanel` の `recompute` を選択行のみ集計に変更）。
ボタンは「✓ 金額を確定」→「✓ 3件の金額を確定し、1件を差戻し」に変わる。

### 5-3. 分離の可視化

- 分離先（REQ-B）の詳細画面：プールパネルに「この申請は **REQ-A** の明細から分離されました」を表示し、元申請へのリンクを張る。
- 元申請（REQ-A）の詳細画面：承認履歴に「明細を分離」の行が出る（既存の履歴表示にそのまま乗る）。
- 一覧：分離先には「分離」バッジを付けると判別しやすい（任意）。

## 7. 検証観点

1. 上席ステップで4明細中1件を外して承認 → 元申請は3明細で購買見積へ、分離先が1明細でプールに出る
2. 購買見積で1件を外して金額確定 → **残り3件の単価だけが保存され**、合計・消費税・税込が3件分になる
3. 同上で、分離先の明細の単価が0にリセットされている
4. 総務部長ステップで11万円→8万円になる分割 → **社長決裁ルートが維持される**（決定どおり）
5. 分離先を再提出 → 上席から通常フローが始まる
6. 分離先をプールで編集・削除できる（既存のプール権限がそのまま効く）
7. 全明細の選択解除 → エラーになり、何も書き込まれない
8. 明細1件だけの申請 → 分割ボタンが出ない
9. **2つのタブで同じ申請を開き、片方で明細を修正 → もう片方で分割を実行 → 不一致エラーで中断し、明細も申請も壊れない**
10. 分割後、元申請のPDFが再生成され、明細が3件になっている（総務部長→社長のようにPDFを生成しない遷移でも再生成されること）
11. 分割後、承認履歴に「明細を分離」が残り、分離先の履歴に差戻し理由が残る
12. 購買手配ステップでは分割UIが出ない
13. 全画面（社長決裁）モードでは従来どおり全体承認・全体差戻しのみ
14. 分離先の申請から**さらに分割はできない**（明細1件のため）
15. `npm run check` が通る

## 8. 限界・運用で補う点

- **既に送信済みのメールに添付されたPDFは古い明細のまま**。分割後の最新PDFはアプリ内から参照できるが、過去メールの添付は差し替わらない。分割時の承認依頼メールに一文を入れて注意を促す。
- **社長決裁ルートは金額が下がっても維持される**（決定事項）。運用で「金額が下がったので社長決裁を省きたい」場合は、1段リコールで購買見積へ戻して金額を確定し直せば経路が組み直される。
- **承認済みの人が承認したのは分割前の申請**。履歴とPDFに分離の事実が残るため追跡は可能だが、「誰がいくらの申請を承認したか」を厳密に問う場合は履歴を読む必要がある。

## 9. 今回のスコープ外（将来の選択肢）

- **承認を伴わない単独の部分差戻し**（「1件だけ戻して、残りはこのステップに留め置く」）。今回は「承認＋分離」に絞る。必要になれば同じコアをもう1つのエントリポイントから呼ぶだけで追加できる。
- 購買手配ステップでの分割。
- 分離先を元申請へ戻して再統合する機能。
