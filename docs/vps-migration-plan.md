## 1. 結論

アプリを、社内のほかのアプリと同じ VPS（Hostinger の業務用 VPS）に移すことをおすすめします。
データはスプレッドシートから PostgreSQL（データベースの一種）へ移します。
画面は今の見た目と操作をそのまま残し、裏側のしくみだけを作り直します。
遅さの原因は、スプレッドシートを読み書きするたびに 1 回 0.15〜1.5 秒の待ちが出ることです。データベースに替えれば、この待ちはほぼなくなる見込みです。
PDF 作成とメール送信は、画面の応答とは切り離して裏で処理します。
期間は準備から切り替えまで、おおよそ 2.5〜3.5 か月の見込みです。
切り替えは並行稼働をせず、リハーサルを重ねたうえで 1 日で行う案を推します。

## 2. なぜ移行するか

### 2-1. 実測（確認済み・2026-11-24 本番の GAS 実行数画面）

| 操作 | かかった時間 |
|---|---|
| アプリを開く（合計） | 約 8〜10 秒 |
| `getTabCounts`（タブの件数。操作のたびに毎回呼ぶ） | 3〜6 秒 |
| `getRequestDetail`（申請の詳細を開く） | 4〜8 秒 |
| 新規申請・編集 | 7〜11 秒 |
| 見積確定・手配完了 | 12〜15 秒 |
| 承認 | 14〜22 秒 |

### 2-2. 遅さの正体（確認済み）

`Diagnostics.gs` の `perfProbe` で内訳を測りました。

- スプレッドシートを開く（`SpreadsheetApp.openById`）: 約 1.3 秒
- シートを 1 枚読む: 150〜700ms。申請 222 行で 0.7 秒、履歴 1774 行で 1.5 秒、小さいマスタでも各約 0.16 秒
- 読んだ後の計算: 数 ms

つまり、時間のほとんどはスプレッドシートとのやり取りの待ちです。
コードを見ると、書き込むたびに読み込みのキャッシュを捨てています（`Storage.gs` の `invalidateCache_`）。そのため 1 回の承認の中で、同じシートを何度も読み直しています。

### 2-3. 承認が特に遅く、ほかの人まで待たされる理由（確認済み＋推測）

- 確認済み: 承認・見積確定・手配完了などの書き込みは、アプリ全体で 1 本だけの鍵（`LockService.getScriptLock()`）を持って処理します。
- 確認済み: その鍵を持ったまま、PDF 作成（HTML→PDF 変換、Drive への保存、古い PDF の削除）とメール送信をしています。該当は `Workflow.gs` の `approveRequest`、`dispatchApprovalNotifications_`、`completeAndNotify_` です。
- 推測: このため、誰かが承認している 14〜22 秒の間、ほかの人の申請や承認は順番待ちになります。待ちが 30 秒を超えると、`waitLock(30000)` でエラーになる可能性があります。

### 2-4. GAS のままでは限界がある理由（推測）

GAS でも、鍵の外で PDF やメールを処理する、件数をまとめて返す、などで数秒は縮められる見込みです。
しかし「スプレッドシートを開くだけで約 1.3 秒」という土台の待ちは、GAS の中では消せません。
データが増えるほどシートの読み込みも遅くなります（履歴 1774 行で既に 1.5 秒）。

### 2-5. 移行後の目標（目標案。オーナーに決めてもらう値）

- 画面の切り替え・詳細表示: 1 秒以内
- 承認・申請などのボタン: 押してから 2 秒以内に画面が戻る（PDF とメールは裏で数十秒以内に終える）

### 3-2. 業務フロー（確認済み）

経路は次のとおりです。

- 申請時: 上席 → 購買（見積）→ 総務部長 → 購買（手配）→ 完了
- 購買が金額を確定し、税抜合計がしきい値（初期 100,000 円）以上なら、総務部長と購買（手配）の間に社長が入ります。判定は「以上」です（`confirmQuote` の `total >= threshold`）。設定シートの説明文は「超過判定」となっており、表記が食い違っています。
- 金額は税抜で保存し、消費税（10%）と税込は表示のときに計算します。

業務の操作は次のとおりです。

| 操作 | サーバーの関数 | できる人 | 裏で起きること |
|---|---|---|---|
| 新規申請 | `createRequest` | 全員 | 上席へ承認依頼メール |
| 差戻し中の編集・保存 | `updateRequestDraft` | 全員（差戻し中のみ） | なし |
| 金額確定前の明細修正 | `updateRequestInReview` | 全員（上席・購買見積のステップで、金額免除でないとき） | 現在の承認者へ「内容更新」メール、履歴に変更内容 |
| 再提出 | `resubmitRequest` | 全員（差戻し中のみ） | 上席へ承認依頼メール |
| 承認 | `approveRequest` | 現在の承認者、同じステップの承認者マスタ・上席マスタの人、管理者 | 次の人へ承認依頼。購買（見積）や購買（手配）に進むときは押印済み PDF を作って添付。完了なら PDF を作り直し、総務部と申請者へ通知 |
| 見積確定（単価入力） | `confirmQuote` | 購買担当・管理者 | 金額確定、しきい値判定で経路を組み直し、総務部長へ承認依頼、総務部へ通知 |
| 金額不要・至急 | `confirmExpedited` | 購買担当・管理者 | 社長を通さず総務部長へ。件名に「至急」の帯を付けたメール |
| 手配完了 | `arrangeComplete` | 購買担当・管理者 | 完了。PDF を作り直し、総務部と申請者へ通知 |
| 差戻し | `returnRequest`（discard=false） | 現在の承認者 | 差戻しプールへ。申請者へ差戻しメール、通知宛先マスタの全員へ「差戻し共有」 |
| 却下 | `returnRequest`（discard=true） | 現在の承認者 | プールに入れず取消にする。申請者へ却下メール |
| 部分差戻し（明細の分離） | 承認・見積・社長決裁の中で `returnItems` を渡す | 同上（購買手配と kiosk では不可） | 選ばなかった明細を新しい申請としてプールへ。元の申請の PDF を作り直す |
| 1 段リコール | `recallStep` | 現在の承認者、このステップへ進めた本人、管理者（先頭のステップでは不可） | 1 段戻して、戻した先の担当へ承認依頼メール |
| 取消 | `deleteRequest` | 管理者は常に。申請者本人は完了前まで。差戻し中は誰でも | 状態を「取消」にし、PDF を Drive のゴミ箱へ |
| 社長決裁の記録 | `recordPresidentDecision` | 社長・管理者。kiosk では社長名で記録し、操作した人を注記 | 承認なら承認と同じ流れ、差戻しなら差戻しと同じ流れ |
| PDF 再作成 | `generateRequestPdf` | 完了済みの申請に関わった人 | PDF を作り直す |

落としやすい細かい決まり（確認済み）:

- 部分差戻しでは、明細を `{ itemId, lineNo, name }` の 3 点で照合します。明細を保存し直すと `itemId` が毎回変わるためです（`docs/item-level-approval-split-design.md` 3-1）。新しいアプリでは明細に変わらない ID を持たせ、この弱点をなくせます。
- 購買見積での分割は、残った明細の合計でしきい値を判定し直します。総務部長・社長での分割は経路を変えません。
- 承認の遷移先（次の承認者）は、分割より前に決めておきます。GAS にはトランザクション（まとめて取り消せる処理）がないためです。新しいアプリでは、データベースのトランザクションで中途半端な状態を防げます。
- 現在の承認者のメール欄には、古い案件だとカンマ区切りで複数のメールが入っています。
- 申請 ID の形式は `REQ-年月日時分秒-6桁`（例: `REQ-20261015132706-091083`）です。

### 3-3. 権限（確認済み）

- ログイン: `Session.getActiveUser()` で社内 Google Workspace のメールを取ります。公開範囲は「ドメイン内のユーザー」です。
- 閲覧: ログインした人は全申請を見られます。
- 管理者: 設定の `adminEmails`（カンマ区切り）。空欄だと全員が管理者になります（初期設定用）。管理者は進行中のどのステップでも操作できます。
- 承認できる人: 「凍結された現在の承認者」に加えて、承認者マスタ・部署別上席マスタで同じステップに登録された人（1 部署に複数人、誰でも対応可）。
- 上席の決め方: 部署別上席マスタの部署名と申請の部署名が完全一致した行。なければ `*`（全社）、さらになければ承認者マスタへ戻ります。

### 3-5. PDF（確認済み）

- `PdfTemplate.html` を HTML で組み、GAS の変換で PDF にします。A4、モノクロ基調で、押印だけ朱色です。
- 押印: 申請者と経路の各ステップに丸いデータネーム印（姓・令和の日付・役職）を出します。差戻しは点線の印です。購買の印は承認者マスタの購買氏名で出します。
- バーコード: 申請 ID から作った**飾りの縞模様**です。読み取れる本物のバーコードではありません（`Pdf.gs` の `barcode`）。
- 作るとき: 購買（見積）に進むとき、購買（手配）に進むとき、完了のとき、分割のとき、手動の再作成のとき。
- 保存: Drive の PDF フォルダの中に申請日ごとのサブフォルダを作って置きます。1 申請 1 ファイルで、作り直すと古いものはゴミ箱へ移します。申請の行に `pdfFileId` と `pdfUrl` を記録し、履歴にも URL を残します。

### 4-2. 全体の形（おすすめ）

```
利用者のブラウザ
   │ HTTPS
Cloudflare（証明書・トンネル）
   │
業務用 VPS  /opt/chozouhin/  docker compose
```

| 公開 | Cloudflare Tunnel（`〇〇.lineworks-local.net`） | nginx＋Let's Encrypt でポートを開ける | 社内の標準。ポートを開けずに済む |

### 4-3. 認証

**おすすめ: アプリ側で Google ログイン（OpenID Connect）を行い、社内ドメインに限ります。**

- Google Cloud で OAuth クライアントを作り、種類を「内部」にします。社外のアカウントはそもそもログインできません。
- 受け取った ID トークンの署名、`hd`（ドメイン）＝ `lineworks-local.info`、`email_verified` を確かめます。
- ログインの後は、署名付きのクッキーでセッションを保ちます。Work Report と同じやり方です。
- 権限の判定（管理者・承認者など）は、今のコードの判定をそのまま移します。

ほかの案: Cloudflare Access に Google をつなぐ方法もあります。アプリにログインの部品を作らずに済みます。ただし、社内の Access は「社内 IP ならログインなし」の設定で使っています。このアプリは操作した人のメールが必ず要るので、その設定は使えません。社内での前例（Work Report）がある、アプリ側のログインを推します。

注意: 社長決裁モードのタブレットは、今は総務部長などのアカウントで開いています。新しいアプリでもタブレットで Google ログインが要ります。

### 4-4. 同時に操作したときの安全（今の ScriptLock の代わり）

- 申請 1 件ごとに、データベースの行ロック（`SELECT … FOR UPDATE`）をかけます。別の申請の操作は待たされません。
- 状態の変更と履歴の追加は、1 つのトランザクションでまとめて確定します。途中で失敗したら全部取り消されます。
- PDF とメールは、確定の後に「仕事の予約」として worker に渡します。画面はすぐ戻ります。
- 画面を開いた後に他の人が変更していたら知らせます。**今の `version` 列はアプリの版（'1.0.0'）が入るだけで更新回数ではないため、更新回数の列を新しく作ります**（Workflow.gs:79）。

### 4-6. PDF の作成と保存

作成:

- **おすすめ: 今の `PdfTemplate.html` を使い、ヘッドレス Chromium（Playwright）で PDF にします。** CSS の再現度が高く、朱色の印（`print-color-adjust`）もそのまま出せます。

- 日本語フォント（Noto Sans JP／Noto Serif JP など）をコンテナに入れます。GAS の変換とは描画の仕組みが違うので、見た目は新旧を並べて確かめます。
- バーコードは、今の飾りの縞模様をそのまま残すのが最小です。読み取れる本物（Code128 など）にするかは、オーナーに決めてもらいます。

保存先:

| 順 | 案 | 長所 | 短所 |

| おすすめ | VPS のディスクに保存し、アプリ経由で見せる（ログインした人だけ） | 速い。Google の API の待ちと権限の管理がない | バックアップを自分で取る必要がある |

- 移行のときに、決まった値の一覧にない値が 1 件でもあれば止めて報告します。

ほかの案: DB には英語のコードで入れ、表示のときに日本語にする方法もあります。DB を直接見る人がいなくなるので可能ですが、変換の箇所が増え、取り違えの危険が増えます。

## 6. 切り替え計画

### 6-1. 並行稼働はしない案を推します

新旧の 2 つで同時に申請を受けると、データが 2 か所に分かれます。承認の途中の申請がどちらにあるか分からなくなります。
そのため、本番の利用者に 2 つを並行して使ってもらうことはしません。
代わりに、切り替えの前に次の 2 つを行います。

- テスト用の環境で、本番データの写しを使ったリハーサル（2 回以上）
- 購買・総務・上席の数人に、テスト用の環境で実際の流れを一通り試してもらう受け入れテスト

### 6-2. 切り替え日の決め方

- 申請と承認が少ない日を選びます（例: 金曜の夕方から週明けの朝まで）。候補日は 〇月〇日【要確認】です。
- 月末や年度末など、購買が忙しい時期は避けます。
- 2 週間前までに、利用者へ案内を出します（新しい URL、ログインの方法、変わらない点）。

### 6-3. 当日の流れ

1. GAS 版を「読み取り専用」にします。そのために、GAS に「メンテナンス中は書き込みを止める」設定を事前に足しておきます（小さな変更）。
2. 最終のデータ移行を行い、5-6 の確かめをします。
3. 新しいアプリで、管理者が数件の動作を確かめます（メールはテスト用の宛先で）。
4. 社内ポータルの「貯蔵品購入部品申請」のリンクを新しい URL に差し替えます。差し替える人は【要確認】です。
5. GAS 版の画面を「移転しました」の案内に替えます。`?requestId=…` 付きで開かれたら、新しいアプリの同じ申請へ案内します。切り替え前に送ったメールのリンクも、これで生きます。
6. 利用者へ切り替え完了を知らせます。

### 6-4. 進行中の申請

- 承認の途中・差戻し中の申請は、ステップと現在の承認者をそのまま移し、新しいアプリで続けます。
- 移した直後に、進行中の申請の承認者へ承認依頼メールを送り直します（9-1 で決定）。購買の段の申請に、見積依頼・手配依頼を PDF 付きで送り直すかは未決です（抜け調査 Q14）。

### 6-5. 元に戻す手順（ロールバック）

- 戻せる期間を、切り替えから 〇 営業日までと決めます【要確認】。
- 戻すと決める人は、オーナーです。
- 手順:
  1. 社内ポータルのリンクを GAS 版に戻します。
  2. GAS 版の読み取り専用を外します。GAS 版のコードと本番 @93 は手を付けずに残しておきます。
  3. 切り替えの後に新しいアプリで増えた申請・履歴を、スプレッドシートへ書き戻します。このための書き戻しの道具を、切り替え前に作ってリハーサルしておきます。
- 戻せる期間を過ぎたら、GAS 版のスプレッドシートは読み取り専用の記録として残します。

### 6-6. GAS 側の改善との並行

- GAS 側の改善は、移行が終わると使わなくなる前提で、効果が大きく小さな変更に絞ります（例: 鍵の外で PDF とメールを処理する）。
- 実施済み・試行中（2026-11-24）:
  - 見出し確認の省略（@91 で本番反映）。効果は小さかった（一覧 4→2.5 秒）。
  - シート内容の一時保存（CacheService）。開発版の実測で、件数 0.23 秒・初期表示 0.40 秒・一覧 0.15 秒・詳細 0.55 秒（エディタ実行の値。画面では通信分が上乗せ）。書き込み（承認など）は速くならないため、移行の必要性は変わりません。
- シートに列を足すなどの変更をしたら、移行の対応表（5-2）にも必ず反映します。移行の作業が始まったら、列の追加はなるべく止めます。

| 外部シートへの共有がされない | 作業員・上席が取り込めず、申請者を選べない | シートの持ち主に、サービスアカウントの共有を頼む。切り替え前に同期を確かめる |

| 同じ VPS のほかのアプリに影響する | ほかの業務も止まる | 社内の決まり（`docker system prune` や `apt upgrade` をしない、Tunnel 名をアプリごとに分ける）を守る。メモリの使い方を確かめる |
| インターネットに公開される | GAS は Google の中に閉じていたが、VPS は外から届く | 社内ドメインのログインを必須にする。Cloudflare の保護を使う。公開前にセキュリティの点検をする |
| バックアップが失敗しても気づかない | データを失う | 大きさの確認と通知、月 1 回の戻す練習 |
| 保守の担当がいない | 障害やアカウントの期限切れで止まり、誰も気づかない | 8-2 で担当を決める |
| GAS 側の改善と二重の作業 | 手間が増える、移行の対応表がずれる | 6-6 のとおり、GAS 側は小さな変更に絞る |

### 8-2. 運用・保守で決めること

- サーバーを見る人（障害の通知を受け、最初に対応する人）
- アプリの直し・機能追加を頼む窓口と、レビューする人
- Google Cloud（OAuth クライアント・サービスアカウント）と Cloudflare の持ち主のアカウント。個人のアカウントに寄せない
- 秘密情報（`.env`、鍵）の保管場所と、知っている人
- バックアップの置き場所と、戻す練習をする人
- 利用者からの問い合わせ先
