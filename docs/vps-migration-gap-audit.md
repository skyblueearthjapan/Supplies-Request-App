# VPS 移行の抜け調査（2026-11-24）

対象: `docs/vps-migration-plan.md`（移行計画書）。方針は「今の機能と使い勝手をまったく残したまま、GAS を VPS に置き換える」。
調べ方: 5 つの観点（業務ロジック／画面／メール・PDF／データ・マスタ・運用／経緯の資料）で、コードを全行と、docs・git 履歴・メモを読み、計画書と突き合わせた。
本番には触れていない（読むだけ）。「推測」と書いた点は、現行 DB や本番の PDF で確かめる必要がある。

**結論:** 計画書は骨組み（業務の流れ・権限・データ移行元・enum・同期の監視）は押さえている。
一方で、次の 3 種類の抜けが多い。
- 細かい業務ルール
- 宛先や押印の細則
- 切り替え当日の GAS 側の後始末

ほかに、計画書の前提に誤りが 4 つあった（1 章で直した）。

## 3. 機能・仕様の抜け（計画書に足すもの）

出典は `file:line`。W=Workflow.gs, C=Constants.gs, H=Helpers.gs, CL=Client.html, E=Email.gs, P=Pdf.gs, J=Jobs.gs, DS=DeptSupervisors.gs, MD=MasterData.gs, ST=Storage.gs。

### 3-1. 業務ロジック

- **申請者:** 申請者メールは**ログインした人**。申請者の名前は画面で選んだ作業員になる（W:64-65, 1701）。代わりに申請した場合、権限と承認者マスタの照合は操作した人で決まる。申請の履歴の操作者名は作業員名（W:83-91）。
- **承認者マスタの探し方:**
  - 申請者メールの一致 → 部署の一致 → `*` の順に探し、最初に当たった行を使う（W:1931-1955）
  - 役職ごとに、空なら `*` の行で補う（W:2024-2036）
  - 有効の欄が空なら有効とみなす（W:2104）
  - **行の順番に意味がある**
- **社長が未登録の場合:** 申請は通るが、総務部長が承認したときに止まる（W:1794-1810）。
- **購買:** 品目区分によらず、メカ・電気の両方の購買が操作できる（W:1980-1984, 2051）。代表は品目区分で決まる（電気なら電気購買が先、W:1985-1996）。
- **承認と専用の操作:** 購買見積・購買手配の段では「承認」を使えず、専用の操作だけ（W:687-694）。手配完了は、確定金額が 0 より大きいときだけ（至急は除く。W:1058-1062）。
- **入力値の扱い:**
  - 文字数の上限を超えた分は**黙って切る**（部署 100、品名・型式・メーカー 200、備考 500、理由詳細 2000、コメント 1000）
  - 明細行は、すべての欄が空なら捨てる。品名は必須。数量は `<= 0` だけをはじく（小数は通る）
  - 単価は、送られてこない明細は今の値を使う。金額＝四捨五入(数量×単価)
  - 消費税は**切り捨て**で、税抜の合計に 1 回だけかける（H:234-248）
  - 「税抜10万円以上」の文言はしきい値によらず固定（W:948, 962）
- **金額確定前の明細修正（W:155-209, 1715-1792）:**
  - 直せるのは明細だけ。単価・金額は送られてきても 0 にし、合計も 0 に戻す
  - 変更がなければ何も書かず、メールも出さない
  - 変更の要約の形式は「明細N 項目: 旧→新」
- **一覧（W:275-347）:**
  - 種類は mine（既定）/pending/supervisor/quote/gm/president/arrange/returned/all の 9 つ
  - 取消は mine と all にだけ出す
  - 検索の対象は ID・申請者・部署・理由詳細・担当者名。**品名・型式は対象外**
  - 並びは更新日時の新しい順で、**最大 200 件**
- **件数バッジ（W:1380-1428）:** 取消は数えない。全員に同じ数を出す。一覧と同じ条件で数える。
- **詳細:** 権限 14 種（`permissions`）、各段の役職、購買の印の名前、分離元の申請 ID を返す（W:387-404）。
- **分割（W:417-674）:**
  - できるのは上席・購買見積・総務部長・社長の段で、**明細 2 件以上**
  - コメント必須。全件を選ぶとエラー
  - 分離先の申請の中身（状態は差戻し、段は申請者、合計 0、単価 0、元の申請から写す項目）
  - 分離先の履歴は 2 行。元の申請の履歴の文言も決まっている
  - PDF を作り直す条件
- **リコール（W:1194-1313）:** 購買見積へ戻すときは「金額不要」の印を外し、経路を標準に戻す。合計は**わざと残す**。「進めた本人」の判定のしかたも移す。
- **再申請（W:211-273）:** 経路を組み直し、合計を 0、PDF の参照を空にする（**ファイルは消さない**）。金額不要の印は戻さない（Q10）。
- **取消・却下:**
  - 管理者は**完了済みも**取り消せ、PDF をゴミ箱へ移す（W:1318-1378）
  - 却下は取消にするが、段はそのまま残す（W:1118-1145）
  - 差戻しでは PDF を消さない
- **決まった文言:** エラー文言は約 30 種。コメント必須の操作は、差戻し・却下・リコール・分割・社長差戻し。それ以外は任意。
- **ID と日時:**
  - ID は `REQ-yyyyMMddHHmmss-6桁の乱数`（日本時間。ITEM-/HIS- も同じ形）。重複は確かめていない
  - 日時は `yyyy-MM-dd HH:mm:ss`（日本時間、時差の表記なし）の文字列
  - 表示名は**メールの @ より前**（H:43-60）

### 3-2. 画面

- **GAS 特有の仕組みの置き換え:**
  - `include()` のテンプレート（Index.html:7,45）
  - `INITIAL_REQUEST_ID`（Index.html:43）
  - `setTitle`（タブ名）
  - `XFrameOptionsMode.ALLOWALL`（ほかのページへの埋め込み許可）
  - `<base target="_top">`
  - `google.script.run`（`gas()`。エラーの日本語の文をそのまま返す形にする）
- **`?requestId=` で開く動き:** ログインを経ても保つ（OIDC の state で戻り先を持つ）。ログインが期限切れになったときの扱いも決める。
- **スマホ表示:** GAS はページの中の viewport の指定を無視する（Code.gs で `addMetaTag` を使っていない）。そのため、今のスマホは PC 幅を縮めた表示と見られる（推測）。**移行すると初めてスマホ向けの配置が効き、見た目が変わる。** 実機で確かめる。
- **日時の渡し方:** API は日付・日時を**今と同じ文字列の形**で返す（ISO の `T` や時差の表記を混ぜない）。画面はこの文字列を切って使っているため（CL:1294, 1282）。
- **PDF の完成を画面に出す:** 後回しで作った PDF のリンクを画面に出す仕組み（今は `refreshDetailIfIdle`）を、worker でも作る。
- **二重押し:** 今は防いでいない。サーバー側の冪等キーかボタンの停止で防ぐ。
- **管理画面:**
  - 承認者マスタは役職ごとのカードで、1 人 1 行に広げて表示し、保存で部署ごとにまとめ直す。2 人目以降の氏名は保存されない
  - **保存で申請者別ルールの列と上席の列が空に戻る**（CL:1841）
  - `*` に役職が欠けていると警告する
  - 保存は 3 回の呼び出しに分かれている（1 つのトランザクションにまとめる）
  - 同期の最終日時の表示は新しく作る
- **説明文の直し:**
  - しきい値の「超える」（CL:1645）→「以上」
  - 「Googleドライブに保存されます」（CL:859）
  - 取消の確認文の「PDFは削除されます」
- **プレビューのバーコード:** 画面のプレビューにも飾りのバーコードがある（CL:1402-1412）。PDF と一緒に直す。
- **見た目・文言・既定値:** 移植すれば残る。受け入れテストの確認表に 1 行ずつ入れる（CL の各所。画面担当の調査で 86 項目）。

### 3-3. メール

- **宛先の細則:**
  - 1 人 1 通で送る
  - 上席の「通知メール」は Cc（To と同じなら付けない）
  - 見積依頼・手配依頼は、To＝品目区分の主担当で送信区分が To の人、Cc＝主担当の Cc ＋ もう一方の購買の全員。`*` の行は見ない
  - Cc だけのときは To へ上げる
  - 同じメールの重複の扱いは、差戻し共有は To を優先、総務部への通知は先に出た方を使う
  - 申請者・編集した本人は宛先から除く
- **送るとき:** 部分差戻しでも、差戻しのメールと差戻し共有を送る。
- **件名:** 種類がある（`【★至急・要社長決裁★】` `【🚨至急・要社長決裁🚨】` `【⚡至急承認・金額確定不要⚡】`）。絵文字は RFC 2047 で送る。
- **完了メール:** 本文に PDF の URL が入る。VPS ではログインが要るリンクになる。
- **後処理の失敗メール:** 通知設定を見ずに送る。
- **送らない操作:** 取消、差戻し中の保存、PDF 再作成、見積確定のときの申請者への連絡。
- **送信の記録:** 今は imaizumi@ の「送信済み」で確かめている。SMTP リレーでは残らない見込み（推測）なので、アプリの中に To・Cc・件名・時刻・結果を記録する。

### 3-4. PDF

- **作る場面と作らない場面:**
  - 作る: 購買見積へ、購買手配へ、完了、分割、手動
  - 作らない: 新規、見積確定（分割なし）、至急、リコール、差戻し、社長へ
- **印に出す名前:**
  - 承認した人の印は、履歴の操作者名
  - 購買の印は、**電気の案件でもメカ購買の名前**（P:86-88, 208）
  - 印の下の役職は、購買見積の段だけステップ名を出す
- **日付と用紙:**
  - 元号の日付は文字列の先頭 10 字から作る。**DB の時刻型にしたら、日本時間に直してから日付にする**
  - **A4 の 1 ページに収める**（2 ページにあふれた不具合があった）
- **Chromium で作るときの設定:**
  - `printBackground: true`
  - 日本語フォントの既定を Noto CJK JP にする（中国語の字形を避ける）
  - ✓ — → ¥ が出るか確かめる
- **ファイル名:** 日本語を含むので、ダウンロードは RFC 5987、メールの添付は RFC 2231 の形にする。
- **保存先:**
  - 申請日ごとのフォルダ
  - 作り直したら古い版を退避する（日数は Q13）
  - 再提出で残っている Drive のファイルの扱い
- **作成中に取り消された場合:** 作った PDF を捨て、メールを止める（P:146-163）。

### 3-5. データ・マスタ・運用

- **セルの型の化け（読み方を列ごとに決める）:**
  - 作業員コードは数値になり、先頭の 0 が消えている
  - 型番は数値化したものがある（`123.0` にしない）
  - 真偽値は文字列と真偽値が混ざっている。空欄を有効と読む列がある
  - 品目区分は空や英語の値がある
  - 設定のしきい値は数値、通知は真偽値か文字列
- **行の順番を残す（sort_order）:** 承認者マスタ、上席マスタ（先頭の人が代表の承認者）、通知宛先（同じメールは先の行を使う）、同じ日の中の履歴。
- **作業員マスタの同期:** タブは **gid 684189184** で探し、A・B・C・E・F 列を位置で読む（MD:4-44）。
- **上席マスタの同期のくせ（DS:108-199）:**
  - 見出しを部分一致で探す
  - 見つからなければ A 列を部署、B 列をメールとして読む
  - タブがなければ `approver` を含むタブを使う
  - 無効と読む値は `false/0/no/×/無効`
  - 新旧で同じ結果になる照合テストを先に作る
- **同期の権限:** 同期の API は、今は誰でも呼べる。新システムでは管理者と worker だけにする。
- **失敗した後処理:** 一覧と消去の画面を作る（`listFailedJobs` / `clearFailedJobs` の代わり）。
- **後回しの仕事の置き換え:**
  - 状態の変更と**同じトランザクション**で積む
  - 実行するときに状態を照合する（差戻し共有と分割の通知は照合しない）
  - 同じ申請の PDF は 1 本ずつ作る
  - リンクの URL は公開 URL に固定する
- **GAS の都合で入れた仕組みは置き換えない:** 共有キャッシュ、見出しの確認、9KB の制限、4 分の上限、`clearSharedCache`。

### 3-6. 切り替え・移行の手順（6 章に足すもの）

- **読み取り専用にした後:**
  - GAS の後回しの仕事（`JOB_*`）が**空になるまで待つ**
  - `JOBFAILED_*` を一覧にして引き継ぐ
- **GAS のトリガー 3 つを止める:** `syncWorkersMaster`、`syncDeptSupervisorsMaster`、`runDeferredJobsSweep`。元に戻すときは再開する。
- **取り込みの道具:**
  - 移行先が空でなければ止まる（移行先を消してから書く道具で、全データを消す一歩手前まで行った前例あり）
  - 接続先が未設定なら起動しない
  - ステージングが本番の DB・PDF の置き場・メールを指していないかを確かめる
  - 同じ requestId の行が重なっていたら止まる
  - 列は見出し名で照合する
- **書き戻しの道具の形（GAS 版を壊さないため）:**
  - 自由入力の列は `'` を付ける
  - 日時は `yyyy-MM-dd HH:mm:ss` の文字列
  - 真偽値は `'true'`
  - routeJson は JSON の文字列
  - version は `'1.0.0'`
  - 列の位置を変えない
- **アプリのコードを前の版に戻す手順:** イメージのタグで戻す。DB の構成の変更とアプリの版は続けて一度に出す。

## 4. 受け入れテストに入れる項目

`docs/manual-test.md` は今の業務フローより前のもので、受け入れ表には使えない。
受け入れ表は、この章、計画書 3 章、split-design 7 章（15 項目）、unit-design 4 章（10 項目）、testing-on-production 3 章から作る。

- **入力:** `3/8` `0123` `=1+1` `1/2` を入れ、画面・PDF・メール・書き戻した後のシートで、入力どおりに出ること。
- **金額:** 税抜 99,999 円と 100,000 円の境目。消費税の切り捨て。至急の案件は社長を通らず、金額なしで手配完了でき、購買見積の印が押されること。
- **明細の項目:** 見積確定・至急・明細修正・分割・再提出の後でも、単位・型式・備考が残ること。
- **リコール・分割・差戻しプール・却下・取消:** 3-1 の各決まりのとおり動くこと。2 つのタブで同時に操作すると止まり、データが壊れないこと。
- **権限:** 担当でない人は承認できないこと（エラー文言も同じ）。Q1 で決めたとおり、全画面モードでも状態と段が確かめられること。
- **件数バッジ:** 各操作と更新の後で、バッジと一覧の件数が一致すること。
- **メール:**
  - 17 種のそれぞれで、To・Cc・宛名・件名・本文・添付が今と同じになること（自動テスト）
  - 宛先の細則（3-3）が守られること
  - 停止の設定が効くこと
  - 失敗しても二重に送らないこと
- **状態の照合:**
  - 承認の直後にリコールしたら、見積依頼も PDF も出ないこと
  - PDF を作っている間に却下したら、PDF が残らず、メールも出ないこと
- **PDF:**
  - 明細が多く履歴が長い申請でも 1 ページに収まること
  - 押印（申請者、実際の上席の役職、購買の氏名）が正しいこと
  - 0 時 30 分に承認したとき、印の日付がその日になること
  - プレビューと実物が一致すること
  - バーコードを 10 回読んで、10 回とも申請番号と一致すること
- **ログイン:** 未ログインで `/?requestId=X` を開き、ログインした後に申請 X の詳細が出ること。
- **同期:**
  - 元が空なら上書きしないこと
  - 作業員コードの先頭の 0 が残ること
  - 管理者以外は同期できないこと
  - 新旧で同期の結果が 1 行ずつ一致すること
- **移行:**
  - 移行先が空でなければ止まること
  - 全申請で、承認経路・承認できる人・担当者の判定が新旧で一致すること（総当たりで比べる）
  - enum の全種類が、決まった値に入ること
- **切り替え:**
  - GAS の後回しの仕事が 0 件で、GAS のトリガーが止まっていること
  - 切り替えの後、GAS から送られたメールが 0 件であること
  - `?requestId=` 付きの古いリンクで、新しいアプリの申請が開くこと
- **スマホ・タブレット:** 新規申請・詳細・全画面・管理画面が実機で使えること。
