## 2. 追加した機能

### (A) 明細の単位（`6bf51cd`）

- `ITEM_COLUMNS` / `ITEM_HEADERS` の**末尾**に `unit` を追加（列位置ベースI/Oのため末尾固定）。
  スプレッドシートの手動移行は不要（`ensureSheet_` が列を自動追加、既存行は空欄のまま許容）。
- 候補は `Constants.gs` の `UNIT_OPTIONS`（個・本・枚・台・箱・ケース・セット・袋・缶・巻・束・組・双・kg・L・m）。
  bootstrap でクライアントへ配布。セレクト＋「その他（自由入力）」方式。
- 表示は**数量セルに併記**（「3 ケース」）。列は増やしていない。
  → 合計行の `colspan`（詳細テーブル5/2、PDF 4/2）を崩さないため、およびPDFの1ページ制約のため。
- 見積パネルは単価入力の右に `/単位` を出し、何あたりの単価かを購買に明示する。

### (B) 金額確定前の編集範囲（`6bf51cd`）

- `canEditInReview_` から `totalAmount <= 0` 条件を撤去し、**ステップ基準に一本化**。
  経路は固定で、金額が確定すると必ず総務部長へ進むため「ステップが上席／購買見積」＝「金額未確定」と同値。
- 塞いだギャップ: `recallStep` で購買見積へ戻すと `totalAmount` が保持されるため、
  **金額を入れ直すために戻したのに明細を修正できない**状態になっていた。
- `updateRequestInReview` は `totalAmount` を0にリセットする（明細の単価・金額が0に落ちるため整合を取る）。

### (C) 明細の部分差戻し＝申請の分割（`c4d283e`）

承認パネル・見積パネルの明細をチェックボックス化。外した明細だけを**新しい申請（status=差戻し）としてコピー**し、
差戻しプールへ移して、残りはそのまま承認を進める。設計の全文は `docs/item-level-approval-split-design.md`。

- 対応ステップ: 上席／購買見積／総務部長／社長（**購買手配は不可**＝発注段階のため）
- 全画面（社長決裁）モードは**分割非対応**（タブレットでの誤操作リスク）。従来どおり全体承認・全体差戻しのみ
- 分離先は通常の差戻し申請と同じもの。既存のプールUI（編集・再提出・削除・件数バッジ）がそのまま動く。
  **新しい状態もタブも追加していない**
- 申請シート末尾に `splitFromRequestId`（分離元申請ID）を追加
- 新しい操作コード `ACTION.SPLIT_OUT: '明細分離'`

**決定事項**：金額確定後（総務部長・社長）の分割では**経路を変えない**（社長決裁ルートを維持）。
金額は減るだけなので必要な承認が飛ばされることはない。
ただし**購買見積での分割は例外**で、`confirmQuote` が確定額から経路を組み直す既存挙動により、
残明細の合計でしきい値を再判定する（高額明細を分離して10万円未満になれば社長決裁は付かない）。

## 3. 実装上のハマりどころ（次に触るとき必読）

### `itemId` は永続IDではない

`replaceItems_`（`Storage.gs`）は明細を**全削除して再挿入し、`itemId` を毎回発番し直す**。
明細を指す操作は `itemId + lineNo + 品名` の**3点セット**で照合し、1件でも合わなければ
**部分実行せず処理全体を中断**する（`resolveSplitSelection_`）。これが同時編集に対する楽観ロックになっている。

### 明細のフィールド列挙は5箇所

明細を書き戻す処理はフィールドを列挙しているため、**新しい列を足したら全部に通すこと**。
1つでも漏らすとその操作の瞬間に値が消える。

`normalizeRequestPayload_` / `normalizeEditableItems_` / `replaceItems_` /
**`confirmQuote` の `rebuilt`** / `SampleData.gs`（2箇所）

### 書き込み順序（分割）

1. **遷移先（経路・次の承認者）の解決を分割より前に行う。**
   分割を確定させた後に「承認者マスタ未設定」等で throw すると、明細だけ分離されて承認は失敗する
   （レビューで発見・修正済み）。
2. **分離先を先に作ってから元申請を書き換える。**
   逆順で落ちると差し戻す明細が復元不能になる。**消失より重複を選ぶ**。
   ただしこの保証が及ぶのは分離する明細だけ。残明細は `replaceItems_` の delete→append の窓が残る
   （分割に限らず明細を書き戻す全操作が元々持つ性質）。
3. `confirmQuote` は**単価適用と分割後の書き戻しを1回の `replaceItems_` にまとめる**。
   先に分割すると `itemId` が変わって単価が付かない。

### PDF の再生成

`dispatchApprovalNotifications_` がPDFを生成するのは次が 購買見積／購買手配／完了 のときだけ。
**総務部長→社長では生成されない**ため、分割時は `regeneratePdfAfterSplit_` が明示的に作り直す。
二重生成を避けるため、生成される遷移では何もしない。

### 分離先の履歴は2件必要

- `ACTION.SUBMIT`（元申請の申請者名義）… PDFの**申請者印**がこの履歴から押されるため
- `ACTION.RETURN`（差戻）… プール画面が `action === '差戻'` から**差戻し理由**を拾うため

## 5. 直した不具合

### メール通知の停止が効かない（`c9d8c9a`）

判定が `String(settings.enableEmailNotifications || 'true') === 'false'` と書かれていた。
設定シートの値はセルの型により**文字列 `'false'` にも真偽値 `false` にもなりうる**
（シートに `false` と入力すると Google スプレッドシートが真偽値へ自動変換する）。
真偽値 `false` は falsy なので既定 `'true'` に落ち、**メールを止めたつもりでも送信され続けていた**。
管理画面のトグルが保存後にONへ戻る症状も同じ原因。

`Helpers.gs` に `emailNotificationsEnabled_` を追加し、判定5箇所（Email.gs 4件・`getBootstrap` 1件）を置換。

### DB統合ツールが運用中に使えなかった（`f65ccb1`）

- `migrateDatabaseToSpreadsheet_` が**スクリプトロックを取っていなかった**。
  アプリの書き込みは全て同じロックを取るため、ロック無しでコピーすると
  「コピー済みのシートへ利用者の書き込みが入った直後に参照先を切り替える」経路が残り、その申請だけ消える。
- `migrateDatabaseToIntendedSheet` は移行先IDを直書きしているため、**サンドボックスで実行すると
  テストデータで本番コンテナを上書き**していた。バインド先が移行先と一致するときだけ実行を許すガードを追加。
- 移行前後の突き合わせ用に読み取り専用の `reportDatabaseRowCounts` を追加。

## 6. 追加したテスト用の仕組み

### メールリダイレクト（`837c9e7`）

スクリプトプロパティ `MAIL_REDIRECT_TO` が有効な間、**全メールを転送先1件だけに送る**。
件名に `【テスト転送】`、本文冒頭に**本来の To / Cc**。Cc は落とし、添付PDFは転送する。

```js
enableMailRedirect()                       // 自分宛て・120分
enableMailRedirect('you@example.com', 30)  // 宛先と分数を指定
getMailRedirectStatus()
disableMailRedirect()
```

- **止めるのではなく寄せる設計**。全停止だとテスト中に発生した本物の通知が失われるが、
  寄せれば手元に届くので手動転送できる。メールの中身と本来の宛先も確認できる。
- **解除し忘れ対策として失効時刻を必ず持つ**（既定120分で自動無効化）。期限の無い値・壊れた値も無効に倒す。
- `MailApp.sendEmail` の呼び出しは全て `sendMail_` 経由に集約済み。
  **今後メール送信を追加するときも必ず `sendMail_` を通すこと**（直接呼ぶとリダイレクトを素通りする）。

### サンドボックス

手順の全文は `docs/testing-on-production.md`。要点だけ:

- **①をコピーするだけ**でコードもデータも入った独立環境になる（コンテナバインドのため）
- コピー後に**必ず**スクリプトプロパティ `DATA_SPREADSHEET_ID` にコピー自身のIDを手動設定する。
  省くとウェブアプリ実行時に `getActiveSpreadsheet()` が null を返し、**アプリが新しいシートを勝手に作る**
  （初期の事故と同じ現象）
- コピー側の設定シートで `enableEmailNotifications=false` / `pdfFolderId` 空欄 / `adminEmails` を自分に
- `setupApplication()` は実行しない（日次トリガーが二重に作られる）
- **コードはコピー時点で固定される**。本番を更新しても反映されないので、新機能を試すときは作り直す

**メール以外の露出経路にも注意**：ステップ別タブ・全申請は全アカウントに全件見え、
`getTabCounts` も全体件数。本番でテストするとバッジが他の人にも見える。PDFもDriveに増える。

## 9. 開発時の注意（前回から継続）

- `clasp push` はマニフェスト差でプロンプト停止することがある → `npx clasp push --force`
- 構文チェックは `npm run check`（`.gs` は `node --check` 不可）
- `clasp login` は失効しうる／`clasp run` は不可（関数実行はGASエディタで手動）
- **enum は日本語の値で照合**（キー名で `hasOwnProperty` しない）
- **税率は `Constants.gs` の `APP.TAX_RATE` と `Client.html` の `TAX_RATE` の2箇所**。必ず一致させる
- 列の追加は**必ず `*_COLUMNS` の末尾**（読み書きが列位置ベースのため）
